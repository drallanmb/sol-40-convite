<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repositório git → mundo | arquivos versionados não podem conter segredos |
| ambiente de build Vercel → backend Convex | deploy key autentica o push de schema/funções |
| deployment preview → deployment produção | precisam usar backends Convex distintos |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Information disclosure | ADMIN_PASSWORD / CONVEX_DEPLOY_KEY vazando no bundle do cliente | high | mitigate | Segredos sem prefixo `VITE_` (Vite só expõe `VITE_*`); nunca referenciados em `src/` (grep gate == 0); ADMIN_PASSWORD só no env do Convex, CONVEX_DEPLOY_KEY só nas env vars de build da Vercel. |
| T-02-02 | Information disclosure | segredo commitado no git | high | mitigate | `.env.local` no `.gitignore` (01-01); `.env.example` só com placeholders; `vercel.json` sem segredos. |
| T-02-03 | Elevation of privilege / Tampering | preview escrevendo na base de produção | medium | mitigate | Deploy keys separadas (Production vs Preview) em escopos distintos da Vercel → cada preview usa backend Convex efêmero isolado. |
| T-02-04 | Denial of service | SPA rewrite mascarando 404 legítimos de assets | low | accept | Rewrite de fallback é padrão para SPA; assets em `/assets/*` (Vite) são servidos antes do fallback; risco cosmético sem dado sensível envolvido. |
| T-02-SC | Tampering | `npx convex deploy` no build (cadeia de deploy) | low | accept | Nenhum pacote novo é instalado neste plano; a cadeia de deploy usa o `convex` já verificado/pinado em 01-01. |
</threat_model>
